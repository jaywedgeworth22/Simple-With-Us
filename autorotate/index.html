What's inside

  • Connectors. Infisical projects, files, Apple Keychain, Android Keystore, HTTPS webhooks -- one rotation envelope covers them all.
  • State machine. LOCK the previous version, ROTATE to new material, PUSH to the target store, VERIFY the new value round-trips, COMMIT the audit record, then AUDIT the chain. Every transition is durable.
  • Zero plaintext. All secret material stays in process memory during a rotation. Nothing is checkpointed to disk, logs, or the database. Crashes abort the rotation rather than leak.
  • Hash-chained audit. Every rotation produces a tamper-evident record hash-linked to the previous one. Breaks in the chain are loud, not silent.
  • Native apps. iOS and macOS for the credentials you actually use on Apple hardware; Android for the keystore you hand to the agent; a web control center for the policy and approval path.
  • Offline-tolerant. A desktop agent queues rotations when the target store is unreachable and replays them deterministically on reconnect -- no double-rotate, no missed-rotate.

How it works

Autorotate is built around the principle that any rotation must be auditable end-to-end, reversible on any failure, and never expose plaintext at rest. Every connector goes through the same six-step pipeline:

  1. LOCK. Acquire a transaction lock on the previous credential so two rotations cannot race. Lock TTL is short; rotation must complete inside the window.
  2. ROTATE. Generate new material inside the agent process. Use the connector's native generator when one exists (Keychain & Keystore prefer platform entropy; HTTPS webhooks require a server-issued nonce).
  3. PUSH. Write the new value into the target store via the store's authenticated API. The agent never reads the old value back in plaintext.
  4. VERIFY. Round-trip the new value: read it through a separate code path, decode the same payload, confirm it matches the rotation envelope. A failed verify rolls back the PUSH.
  5. COMMIT. Append a hash-chained audit record. The record contains the rotation IDs, target IDs, timestamps, and the chain hash -- never the secret material itself.
  6. AUDIT. Notify the policy layer (web control center, Slack if configured, or webhook subscribers) and unlock the previous credential.

If the rotation fails at any step the state machine aborts, releases the lock, and emits a structured error. No partially-rotated credentials remain in the target store.

Mac version

Autorotate for Mac is the desktop agent -- the service that holds the lock window, generates new material in process memory, pushes to every connected target, and round-trips the verify before committing the audit record. It runs as a launchd-managed service. Connectors plug in via ~/Library/Application Support/Autorotate/connectors/; the web control center publishes a token you paste on first run.

Direct download (DMG). Email feedback@simplewithus.com for the build link until the notarized installer is published.

What it doesn't do

  • No plaintext on disk. Secret material lives only in memory during a rotation and in the destination store (Infisical, Keychain, Keystore, or the webhook target). Autorotate's own database stores identifiers, hashes, and the audit chain only.
  • No background rotations. Every rotation is explicit. Schedules exist but they require the operator to compose an action; nothing rotates silently on a timer.
  • No key escrow. Autorotate never sees your credentials in a form that lets it impersonate them to your services. It only writes what you've authorized it to write, into the stores you've connected.
  • No plaintext logging. Logs are scrubbed for secret-shaped strings before they leave the agent. Crash reports are opt-in.

Privacy

Autorotate never persists plaintext secrets. Audit records are hash-chained and tamper-evident; the chain head is signed on every commit. No telemetry, no analytics. Crash reports are opt-in and scrubbed for anything that looks like a token, key, or password.

Need help?

The most common hiccup on first run is the connector authorization -- Infisical needs a service token, Keychain & Keystore need the user to confirm access on first use, webhooks need an HMAC pre-shared key. The support page walks each connector; if those don't help, write to feedback@simplewithus.com with the connector name, the rotation ID, and what you saw.
